# Security

Report suspected vulnerabilities privately to the Wocody maintainer responsible for this project. A public reporting address will be supplied before WordPress.org submission. Do not include real backups, credentials or personal data in public issues.

## Trust boundaries

- Migration is equivalent to installing executable site code. Only administrators with `manage_options`, a logged-in session and a valid REST nonce can operate the plugin. Packages must come from trusted sources; checksums are not signatures.
- Server continuation uses `admin-ajax.php?action=boat_backup_continue` loopback requests without cookies. Each carries a 256-bit secret generated for that job and stored only in private job state; it is compared in constant time. The request can only advance the active job's export or staging steps. It cannot start, unlock, confirm, cancel or restore anything. When loopbacks never arrive, the job falls back to browser-driven steps.
- Password-protected packages encrypt every SQL and file segment with AES-256-GCM using a PBKDF2-SHA256 key (200,000 iterations, random 16-byte salt). Each segment has a random nonce and is bound to its record name, so segments cannot be swapped. The manifest, record descriptors, file names and site addresses stay readable; descriptor checksums cover the encrypted bytes. The derived key, never the password, is kept in private job state until the package has been fully read, then removed.
- Packages contain executable native SQL and site code and must come from a trusted source. The dump parser restricts operations to canonical, declared table targets, validates complete ordering and named literal inserts, and remaps every target to job-owned temporary tables. Native DDL is not restricted by a column-type grammar. Database creation, arbitrary statements and external-resource definitions are refused. The destination server validates native DDL.
- Serialized strings are parsed as bytes. Package objects are never instantiated during rewriting. WordPress option decoding uses `allowed_classes=false` and only accepts string plugin paths.
- ZIP entries are bounded, declared, checksummed and count-checked. Content paths are relative to wp-content; traversal, control characters, symlink ZIP entries and any path inside Boat Backup & Migration itself are rejected. Export follows symbolic links found in wp-content, so a link to a file outside wp-content exports that file's content; links that would loop and broken links are skipped. WordPress drop-ins and hosting must-use plugins in a package are never installed. A package installs executable plugins, themes and must-use plugins, so only restore trusted packages.
- When no private location outside the web root is writable (open_basedir, installation inside a public subfolder) and BOAT_BACKUP_STORAGE_PATH is not defined, storage falls back to `wp-content/boat-backups`. It is protected by index.php, .htaccess and web.config and excluded from exports. Servers that ignore those files (for example nginx) need an equivalent deny rule for that folder; otherwise backups, job state and staged files can be requested by URL. Define BOAT_BACKUP_STORAGE_PATH for stronger isolation.
- Private staging and recovery material must remain outside every public virtual host or alias. The runtime checks the current document root; the host administrator is responsible for other server mappings.
- There is one mutation lock per installation. State changes use temporary files and atomic renames. Every SQL batch has a durable pending-table marker; an interrupted write rebuilds that staged table from its DROP statement. This works independently of engine transaction support. Aria/foreign-reference/option/collation transformations and error-1030 engine fallback are automatic and disclosed in the restore UI.
- Native mysqli preserves raw byte strings; wpdb text sanitation is not applied to SQL payloads. Geometry, BLOB, binary and BIT data bypass URL substitution. BIT values use hexadecimal literals; generated values are recomputed by the server. Connection sql_mode is temporarily cleared and restored after each migration step. An export read error 1194 triggers REPAIR TABLE on the affected source table before retrying it.
- The final switch is one RENAME TABLE statement, after journaled file moves. This is application-level recovery, not a cross-filesystem/database transaction or protection against all hardware failures.
- Source sessions are omitted. The destination's URL, core, database connection, salts and hosting configuration remain local.

## Operational limits

Exports require a quiescent source for cross-request consistency. Existing requests, cron processes and direct static-file serving are not frozen by the plugin. Private storage must be on the content filesystem. DDL or data rejected by the destination stops staging before live replacement. Statement size is bounded by available PHP memory and max_allowed_packet, and oversized statements fail explicitly rather than being silently skipped. An individual row or a server DDL operation can still exceed a host's execution limits.

Backups, old tables and recovery directories may contain password hashes, tokens and personal data. The plugin preserves them on uninstall; administrators must apply their retention policy and delete them deliberately after verifying the migration.
